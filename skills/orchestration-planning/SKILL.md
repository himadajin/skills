# orchestration-planning

サブエージェントへの委譲を前提とした実装計画を立て、
ユーザーのGOサインを得てから、
オーケストレーターとして実装を進めるスキルです。

## 原則

1. GOサイン前に行うのは、
   読み取り専用の調査(調査サブエージェントへの委譲を含む)と、
   作業ディレクトリへの計画・指示書・引き継ぎファイルの書き込みだけです。
   それ以外のリポジトリ状態を変える操作はすべてGO後に行います。
2. 実装と修正はすべてサブエージェントに委譲します。
   オーケストレーターは計画・指示・レビュー・最終合否の判断に専念し、
   自分のコンテキストを判断のために温存します。
3. 各実装成果物は、実装者のバイアスを避けるため、
   実装者と独立した新規コンテキストのサブエージェントにレビューさせます。
   オーケストレーターは差分・検証証拠・レビュー所見を自分でも確認して合否を決めます。
4. commitはレビュー合格の記録として、合格後にオーケストレーターだけが行います。
5. 不確かな情報(モデル識別子、利用可能な機能など)は推測や捏造で補わず、
   計画からの逸脱が必要になったら黙って進めず報告します。
   サブエージェントが使えないと判明したら、自分で代行せず停止して報告します。

## 計画の立て方

1. これまでの会話と参照文書から、合意済みの完了条件と検証方法を確認する。
   合意が確認できない項目は、確認事項として列挙する。
2. 現在のbranch、既存の規約、関連コードと検証手段を読み取り専用で確認し、
   計画をリポジトリの実態に合わせる。
3. 計画をチャットに提示し、作業ディレクトリに自己完結した文書として保存する。
   コンテキスト圧縮後も役割分担を復元できるよう、文書には上記の原則を含める。
4. GOサインを待つ。

作業ディレクトリはユーザーの指定に従い、
なければリポジトリルートのtmp配下にサブディレクトリを作ります。
パスを計画に明記してください。

## 計画が答えるべきこと

以下の観点を、タスクの規模に応じた詳細度で計画に含めます。

- タスク分解:
  サブエージェントに割り当て可能な単位への分解、依存関係、並列可能箇所。
  並列するタスク同士が同一ファイルを変更しない担当範囲の切り分け。
  依存関係と、レビュー・commit・ユーザー承認待ちのゲートが読み取れる
  mermaidのflowchartを添える。
- モデル割り当て:
  各タスクに使うモデルと選定理由。ユーザーの指定があればそれに従う。
- サブエージェントの生存区間:
  各サブエージェントを継続して使い回すか、新規コンテキストで起動するか。
  蓄積すべき知見(規約、落とし穴、失敗パターン)は引き継ぎファイルに外部化すると、
  レビュアーを新規コンテキストに保ったまま活用できる。
- 指示書の方針:
  サブエージェントはこの会話の文脈を知らないため、指示書は自己完結させる。
  タスク単位の完了条件、変更してよいファイル範囲、
  議論で却下済みの設計案を含める。
- レビューとcommitの方針:
  各成果物のレビュー観点、合意済みの検証をどの段階で誰が実行するか、
  レビュー可能な大きさを意図したcommit単位、作業branch。

## GOサイン

GOサインは、提示した計画の承認です。
未合意の完了条件・検証方法・プロダクト上の仮定は計画の承認と混ぜず、
確認事項として分離し、個別に合意を得てください。
