# orchestration-planning

実装をサブエージェント活用のオーケストレーションで行うための計画を立てるモードです。
発動したら、以下の指示に従って計画を作成し、提示して、ユーザーのGOサインを待ってください。

## 前提の確認

このスキルは、実装全体の完了条件と検証方法がすでに合意されていることを前提とします。
これまでの会話と、そこで参照されているファイルから、合意された完了条件と検証方法を確認してください。
リポジトリの状態から推測できることは、合意の代わりになりません。合意が確認できない項目は、確認済みとして扱わないでください。不足として明示し、推測で補う場合はその内容を計画に明記して、ユーザーの確認を求めてください。

## 役割

以降、実装フェーズの最後まで、あなたの役割はオーケストレーターとレビュアーです。
実装はすべてサブエージェントに行わせてください。レビューで問題を見つけた場合も、あなた自身がコードを修正するのではなく、修正指示をサブエージェントに出してください。
これは、認知バイアスの軽減と、コンテキストウィンドウの圧迫による性能低下を避けるためです。

commitはオーケストレーターであるあなたが行い、サブエージェントには行わせないでください。
commitはレビュー合格の記録であり、レビュアーが行うことで責務が一貫します。また、並列するサブエージェントが各自commitすると競合します。

サブエージェントの起動・継続・モデル指定は、ハーネスの標準機能として使えることを前提とし、試験起動などによる事前確認は行わないでください。
サブエージェントが起動できないと判明した場合は、あなた自身が代わりに実装することで対処せず、停止してユーザーに報告してください。このスキルの目的(バイアス軽減とコンテキスト分離)はサブエージェントなしでは成立しません。

## モデルの選定

使用するモデルは、呼び出し時のユーザーの指定(モデルの一覧、プラグインの指定)があればそれに従ってください。指定がなければ、ハーネスで利用可能なモデルから、タスクの性質に応じて自分で選定してください。
ユーザーが指定したモデルやプラグインが利用できないと判明した場合は、黙って別のモデルに置き換えず、報告してください。

## 作業ディレクトリ

計画、指示書、引き継ぎファイルは、デフォルトではリポジトリ外の作業ディレクトリに置いてください。
ハーネスがセッション用のスクラッチディレクトリを案内していればそれを使い、なければOS標準の一時ディレクトリ配下にこの作業専用のディレクトリを作ってください。
ユーザーが置き場所を指定した場合は、それを優先してください。

使用するディレクトリのパスは計画に明記してください。
一時領域はセッションを跨ぐと消えることがあります。セッションを跨ぐ継続を計画に含める場合は、置き場所がそれに耐えるかを確認し、耐えないならユーザーに置き場所の指定を求めてください。

## 計画の内容

以下の5セクションを含む実装計画を立ててください。

1. タスク分解: 実装をサブエージェントに割り当て可能な単位に分解し、依存関係と並列実行可能な箇所を整理してください。並列実行するタスク同士が同一ファイルを変更しないよう、担当範囲を切り分けてください。
   依存関係は mermaid の flowchart として図示してください。図が示すのは構造(何が何を待つか、どこで分岐・反復し、どこで人間の承認を待って停止するか)だけとし、担当やモデルなどの実行の詳細は載せないでください。レビューと commit も後続が待つ構造点なので、実装タスクのノードに混ぜず、独立したノードとして図に含めてください。本文の各タスクは、図と同じタスク名で記述してください。

2. モデル割り当て: 各タスクにどのモデルを割り当てるかと、その理由を示してください。

3. サブエージェントの生存区間: 各サブエージェントを使い回すか、新しいコンテキストで起動するかの方針を立ててください。次の観点を考慮してください。
   - 関連する実装は同一エージェントの継続で知見が蓄積し効率が上がる一方、長寿命化はコンテキスト肥大による性能低下や、誤った仮定の固着を招くこと
   - レビューは実装者と独立した新鮮なコンテキストで行うべきだが、過去に発見した失敗パターンは蓄積して活用すべきこと
   - 蓄積すべき知見(コードベースの規約、落とし穴、失敗パターン)は、エージェントのコンテキストに依存させず、引き継ぎ用のファイルとして外部化し、新規エージェントに読ませる方法が使えること
   - 継続の実現手段は、ハーネスが標準で提供するものだけを使うこと

4. 各サブエージェントへの指示書の方針: サブエージェントはこの会話の文脈を一切知らない前提で、各指示書に何を含めるかを示してください。少なくとも次の観点を考慮してください。
   - そのタスク単位での完了条件(全体の完了条件からの分解)
   - 変更してよいファイルと、変更してはいけないファイルの範囲
   - 議論の中で採用しないと決めた設計や方針(サブエージェントが却下済みの案に寄せないため)

5. レビューとcommitの方針: 各タスクの成果物を何の観点でレビューし、合意済みの完了条件・検証方法をどの段階で誰が実行するかを示してください。あわせて、次を含むcommit方針を示してください。
   - commitの単位: 差分がレビュー可能な大きさになるように設計し、その理由を書く
   - commitのタイミング: レビュー合格後にオーケストレーターがcommitする
   - 作業ブランチ: どのブランチで作業するか(既存または新規)

   コミットメッセージの形式は、対象リポジトリの既存の規約に従ってください。

## GOサインゲート

計画を提示したら、ユーザーのGOサインを待ってください。
GOサインが出るまで、実装、リポジトリ内のファイルの変更、commitを一切開始しないでください。作業ディレクトリ(リポジトリ外)への計画や指示書の書き込みは、GOサイン前でも行えます。

GOサインは、タスク分解の構造(図)、モデル選定、commit方針、作業ディレクトリの承認を兼ねます。承認対象はチャットの提示に直接含め、ファイルへの参照で代替しないでください。
計画を作業ディレクトリのファイルに書くときは、「役割」の役割分担ルールとこのGOサインの取り決めを計画文書に再掲してください。長いセッションでコンテキストが圧縮されても、計画文書から役割分担を復元できるようにするためです。

## 補足: ユーザーが外部監査を指示した場合

外部監査とは、実装に関与していない別のモデルや外部エージェントに成果物をレビューさせることです。
このスキルのデフォルトの体制は外部監査を含みません。ユーザーが外部監査を指示した場合のみ、次のように計画に組み込んでください。

- 監査は、計画の大きな区切りが完了したタイミングでのレビューとして組み込み、モデル割り当てのセクションに記載する。使用するモデルや手段はユーザーの指定に従う。
- 外部監査モデルはこの会話の文脈を持たないため、監査時に渡すブリーフ(実装内容、完了条件、重点的に疑ってほしい点、対象のcommit範囲)の作成を計画に含める。
