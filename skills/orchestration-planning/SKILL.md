# orchestration-planning

このスキルは、オーケストレーションを考慮した実装計画を立てるスキルです。
以下の指示に従って計画を作成し、提示してください。
実装はユーザーのGOサインを待ってください。

## 前提の確認

このスキルは、実装全体の完了条件と検証方法がすでに合意されていることを前提とします。
これまでの会話と、そこで参照されているファイルから、合意された完了条件と検証方法を確認してください。
リポジトリの状態から推測できることは、合意の代わりになりません。
合意が確認できない項目は、確認済みとして扱わないでください。
不足として明示し、推測で補う場合はその内容を計画に明記して、ユーザーの確認を求めてください。

## 計画作成と計画実行の境界

次の順序で進めてください。

1. 会話と参照文書から、合意済みの完了条件と検証方法、不足事項を整理する。
2. 計画をリポジトリの実態に合わせるため、現在のbranch、既存の規約、関連コードと検証方法を読み取り専用で確認する。
3. 調査結果を反映した計画と、ユーザー確認が必要な提案・仮定を提示する。
4. GOを待ち、承認後にだけ実装へ進む。

読み取り調査で得た事実は計画の根拠にはできますが、ユーザーとの合意の代わりにはなりません。
必要なら、計画作成のための読み取り専用調査をサブエージェントに委譲できます。

GO前に起動してよいのは調査担当だけです。
実装・修正担当の起動、branch作成、リポジトリ内のファイル変更、
検証コマンドの実行、commitは開始しないでください。
作業ディレクトリへの計画、指示書、引き継ぎファイルの書き込みだけは例外として許可します。

## 役割

オーケストレーターを最終レビュアーとした計画を立ててください。
実装はすべてサブエージェントに行わせてください。
各実装成果物は、実装者と独立した新しいコンテキストのレビュー担当サブエージェントに検査させてください。
オーケストレーターは差分、検証証拠、独立レビューの所見を自分でも確認し、最終的な合否を決めます。
レビューで問題を見つけた場合も、あなた自身がコードを修正するのではなく、修正指示をサブエージェントに出してください。
これは、認知バイアスの軽減と、コンテキストウィンドウの圧迫による性能低下を避けるためです。

commitはオーケストレーターであるあなたが行い、サブエージェントには行わせないでください。
commitはレビュー合格の記録であり、レビュアーが行うことで責務が一貫します。
また、並列するサブエージェントが各自commitすると競合します。

サブエージェントの起動・継続・モデル指定は、ハーネスの標準機能として提供されています。
試験起動などによるハーネス機能の事前確認は行わないでください。

サブエージェントが起動できないと判明した場合は、停止してユーザーに報告してください。
あなた自身が代わりに実装することで対処することはしないでください。
このスキルの目的(バイアス軽減とコンテキスト分離)はサブエージェントなしでは成立しません。

## モデルの選定

使用するモデルは、呼び出し時のユーザーの指定(モデルの一覧、プラグインの指定)があればそれに従ってください。
指定がなければ、ハーネスで利用可能なモデルから、タスクの性質に応じて自分で選定してください。
計画には、各タスクへ割り当てる選択肢をハーネスが公開する正確な識別子で記載してください。
「高能力モデル」「コーディング向けモデル」「GPT-5系」のような能力カテゴリだけでは、モデル割り当てを完了したことになりません。
利用可能性はハーネスが提示する一覧から判断し、試験起動はしないでください。正確な選択肢を確認できない場合は識別子を作らず、不足として報告してください。
その場合は `モデル割り当て: 未確定（利用可能な正確な識別子を確認できないため）` と記載し、仮の識別子を併記しないでください。
ユーザーが指定したモデルやプラグインが利用できないと判明した場合は、黙って別のモデルに置き換えず、報告してください。

## 作業ディレクトリ

計画、指示書、引き継ぎファイルの配置場所の説明をします。

ユーザーが配置場所を指定した場合は、指示に従ってください。

指示がない場合は、リポジトリのルートのtmpディレクトリに作業用のサブディレクトリを作って、そこに配置して下さい。

使用するディレクトリのパスは計画に明記してください。
一時領域はセッションを跨ぐと消えることがあります。
セッションを跨ぐ継続を計画に含める場合は、置き場所がそれに耐えるかを確認し、耐えないならユーザーに置き場所の指定を求めてください。

## 計画の内容

以下の内容を含む実装計画を立ててください。

1. タスク分解
2. モデル割り当て
3. サブエージェントの生存区間
4. 各サブエージェントに渡す指示書の方針
5. レビューとcommitの方針

詳細は以降で説明するセクションの説明に従ってください。

### 1. タスク分解

実装をサブエージェントに割り当て可能な単位に分解し、依存関係と並列実行可能な箇所を整理してください。
並列実行するタスク同士が同一ファイルを変更しないよう、担当範囲を切り分けてください。

依存関係は mermaid の flowchart で図示してください。
flowchartには以下の内容を含めてください。

- 何が何を待つか
- どこで分岐・反復するか
- レビューとcommitのタイミング
- どこで人間の承認を待って停止するか
- 外部監査が指定されている場合は、監査と監査不合格時の修正経路

また、flowchartには以下の内容を含めないでください。
- 具体的なモデル名
- 実行の詳細

レビューと commit も後続が待つ構造点なので、実装タスクのノードに混ぜず、独立したノードとして図に含めてください。
本文の各タスクは、図と同じタスク名で記述してください。

### 2. モデル割り当て

各タスクにどのモデルを割り当てるかと、その理由を示してください。

### 3. サブエージェントの生存区間

各サブエージェントを使い回すか、新しいコンテキストで起動するかの方針を立ててください。次の観点を考慮してください。

- 関連する実装は同一エージェントの継続で知見が蓄積し効率が上がること。
  一方、長寿命化はコンテキストの肥大による性能低下や、誤った仮定の固着を招くこと。
- レビューは実装者と独立した新鮮なコンテキストで行うべきだが、過去に発見した失敗パターンは蓄積して活用すべきこと。
- 蓄積すべき知見(コードベースの規約、落とし穴、失敗パターン)は、エージェントのコンテキストに依存させず、
  引き継ぎ用のファイルとして外部化し、新規エージェントに読ませる方法が使えること。
- 継続の実現手段は、ハーネスが標準で提供するものだけを使うこと

### 4. 各サブエージェントに渡す指示書の方針

サブエージェントはこの会話の文脈を一切知りません。
そのため、サブエージェントに渡す指示書は自己完結する必要があります。
計画を立てる際は、どのような指示を書くかの方針を示してください。

方針を検討する際は、少なくとも次の観点を考慮してください。

- そのタスク単位での完了条件(全体の完了条件からの分解)
- 変更してよいファイルと、変更してはいけないファイルの範囲
- 議論の中で採用しないと決めた設計や方針(サブエージェントが却下済みの案に寄せないため)

### 5. レビューとcommitの方針

各タスクの成果物を何の観点でレビューし、合意済みの完了条件・検証方法をどの段階で誰が実行するかを示してください。

あわせて、次を含むcommit方針を示してください。
- commitの単位: 差分がレビュー可能な大きさになるように設計し、その理由を書く
- commitのタイミング: レビュー合格後にオーケストレーターがcommitする
- 作業ブランチ: どのブランチで作業するか(既存または新規)

コミットメッセージの形式は、対象リポジトリの既存の規約に従ってください。

## GOサインゲート

計画を提示したら、ユーザーのGOサインを待ってください。
GOサインが出るまでの許可範囲と禁止範囲は「計画作成と計画実行の境界」に従ってください。

GOサインは、タスク分解の構造(図)、モデル選定、サブエージェントの生存区間、指示書の方針、レビューとcommit方針、作業branch、作業ディレクトリの承認を兼ねます。
これらの計画上の提案は、GOで承認を得るまでは確定事項として扱わないでください。
一方、未合意の完了条件、検証方法、プロダクト上の仮定は、計画の承認対象と混ぜず確認事項として分離してください。
GOだけで合意済みに変わるとはみなしません。
承認対象はチャットの提示に直接含め、ファイルへの参照で代替しないでください。
計画を作業ディレクトリのファイルに書くときは、「役割」の役割分担ルールとこのGOサインの取り決めを計画文書に再掲してください。
長いセッションでコンテキストが圧縮されても、計画文書から役割分担を復元できるようにするためです。

## 補足: 外部監査

外部監査とは、実装に関与していない別のモデルや外部エージェントに成果物をレビューさせることです。
現在使用しているハーネスで使用できるモデルやプラグインの中に、オーケストレーターと異なるモデルが含まれていれば、
外部監査を行うことができます。
ユーザーが明示的に外部監査を指示した場合のみ外部監査を行ってください。
外部監査についての言及がない場合は外部監査を行う必要はありません。

ユーザーが外部監査を指示した場合、実装に関与していない別モデルを用意できることを計画の前提にしてください。
用意できない場合は監査を省略したり実装モデルで代用したりせず、停止してユーザーに報告してください。

次のように計画に組み込んでください。

- 監査は、大きな区切りの独立レビュー合格後にオーケストレーターがcommitした成果を対象に行い、
  次の区切りへ進むためのゲートにする。
  commitは内部レビュー合格の記録、外部監査は次工程へ進めるかの独立ゲートとして役割を分ける。
  使用するモデルや手段はユーザーの指定に従う。
- 外部監査モデルはこの会話の文脈を持たないため、監査時に渡すブリーフ(実装内容、完了条件、重点的に疑ってほしい点、
  対象のcommit範囲)の作成を計画に含める。
- 監査不合格時は、実装サブエージェントによる修正、fresh contextでの独立レビュー、
  オーケストレーターによる修正commit、同じ監査ゲートでの再監査、の順に戻す。
